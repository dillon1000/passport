## Why this matters

Passport is the source of truth for identity across "all my other apps", but
today a downstream application only discovers that a user was deleted, banned,
or had organization membership changed at its **next** token refresh or sign-in.
There is no push channel. Better Auth `databaseHooks` in `src/auth.ts` already
fire internally on user creation, account linking, and session creation, and the
codebase already runs a durable Cloudflare Workflow (`DataExportWorkflow`) for
fan-out work — so the event sources and the delivery primitive both exist. The
missing piece is a designed, signed, retried **outbound webhook** layer so
dependent apps can deprovision and react in real time.

This is intentionally a design/RFC plan, not the implementation. Webhooks touch
schema (subscriptions + delivery log), the auth event surface, signing/secret
handling, retry/delivery semantics, and an admin UI. Writing the design first
keeps the eventual build boring and avoids a half-specified event taxonomy that
downstream consumers would have to reverse-engineer.

## Design work to complete

Create `docs/outbound-lifecycle-webhooks.md` answering every section below.

### 1. Problem statement and non-goals

State the concrete problem: downstream apps cannot react to identity changes
until next token refresh; there is no push channel. Non-goals for the first
implementation:

- No inbound webhooks (Passport consuming external events).
- No marketplace/public event catalog.
- No per-event-type fan-out optimization beyond what Workflows give for free.
- No replay UI beyond a basic delivery log in the first phase.

### 2. Event taxonomy

Define a stable, namespaced event list grounded in events Passport already
observes. Recommended first set, mapped to their existing source:

- `user.created`, `user.updated`, `user.deleted` — `databaseHooks.user` and the
  delete-user flow.
- `user.banned`, `user.unbanned`, `user.role_changed` — `worker/index.ts`
  adminUsers `ban`/`unban`/`setRole`.
- `account.linked`, `account.unlinked` — `databaseHooks.account` and
  `securityEventForPath` unlink path.
- `member.added`, `member.removed`, `member.role_changed` — organization plugin
  membership changes.
- `organization.created`, `organization.deleted` — organization lifecycle.

For each event, specify the payload shape (stable field names, IDs not full
objects where an ID suffices, ISO-8601 timestamps) and explicitly state that
**no secrets, tokens, or password material ever appear in a payload**.

### 3. Trigger architecture

Decide and document **how** events are emitted. Recommended: a single internal
"emit event" helper invoked from the existing hook sites in `src/auth.ts` and
from the adminUsers service in `worker/index.ts`, rather than scattering HTTP
calls through the codebase. Document whether emission writes an event row first
(durable, replayable) and then triggers delivery, or triggers delivery directly.
Recommend the durable-first approach to match the `dataExportRequest` precedent.

If recon shows Better Auth ships a first-class webhook primitive, document it and
recommend using it; otherwise recommend the internal-helper approach. State which
one you found.

### 4. Subscription and delivery schema sketch

Sketch (do not create) two tables, mirroring `adminAuditEvent` conventions:

- `webhook_endpoint`: id, owner scope (provider-level vs `organizationId`),
  target URL, signing-secret reference, subscribed event types, enabled flag,
  created/updated timestamps. Note that the signing secret must be stored
  hashed/encrypted, never plaintext, and shown once on creation.
- `webhook_delivery`: id, endpoint id, event type, payload reference, attempt
  count, status, response code, next-retry time, timestamps. Index by endpoint
  and by status for retry sweeps.

Describe migration generation as a CLI step (Better Auth CLI generate +
`pnpm db:generate`), never hand-written SQL.

### 5. Signing and security

Specify HMAC-SHA256 request signing using `crypto.subtle` (Workers-safe),
timestamped signature headers to prevent replay, the verification recipe a
consumer follows, and secret rotation. Address SSRF: target URLs must be
validated (https only, no internal/metadata addresses) before delivery.

### 6. Delivery, retries, and idempotency

Recommend reusing the Workflow pattern from `worker/data-export.ts`
(`WorkflowEntrypoint` + `step.do` + `NonRetryableError` for permanent failures)
or a Cloudflare Queue. Pick one and justify it. Specify retry/backoff schedule,
max attempts, a stable per-delivery idempotency key consumers can dedupe on, and
how a dead delivery is surfaced.

### 7. Configuration and bindings

List the new `wrangler.jsonc` binding(s) the implementation will need (Workflow
or Queue), any new env/secret keys (added to `.dev.vars.example` with one-line
comments per the README convention), and how delivery is disabled when no
endpoints are configured.

### 8. Admin/owner UI surface

Describe where subscription management lives (a new section vs the Applications
page) and what it shows: endpoint URL, subscribed events, one-time secret,
recent deliveries with status. Keep the first pass minimal.

### 9. Implementation phases after design

End with a phased build breakdown, each phase with a verification note and a
rollback note:

1. schema + emit helper (no delivery yet; events recorded only)
2. signing + Workflow/Queue delivery
3. subscription CRUD service + routes + tests
4. admin/owner UI
5. docs + `.dev.vars.example` + README endpoint docs

## Maintenance notes

- This design is the source material for the build plans in section 9. Keep the
  event taxonomy concrete enough that a future executor builds payloads without
  re-deriving field names.
- Plan 018 (back-channel logout) is a **separate** push channel with OIDC-defined
  semantics; do not merge it into this generic webhook layer. Cross-reference the
  two but keep `logout_token` delivery OIDC-compliant rather than a custom event.
- A reviewer should scrutinize the payload shapes for any field that could leak
  PII or secrets, and confirm SSRF validation is part of the design, not an
  afterthought.
