Plans 021-023 were authored on 2026-06-18 from an "open-source Auth0" gap review, scoped to Passport's positioning as the **self-hosted, single-tenant IdP an organization runs to be its own "Sign in with ACME"** (not a SaaS broker). Recon against the pinned `@better-auth/oauth-provider@1.6.18` reshaped all three before they were written:

- **021 (M2M):** the `client_credentials` grant is already a default, `resource`/`audience` (RFC 8707) handling exists, and `oauthApplication` already has a `grantTypes` array column (`src/db/schema.ts:408`) — so the plan is wiring + an audience model + UI/metadata, not building a grant. The `apiKey` plugin is **not exported** at the installed version, so static API keys are explicitly deferred; `client_credentials` is the one M2M path.
- **022 (introspection/revocation/rotation):** `/oauth2/introspect` (7662) and `/oauth2/revoke` (7009) are already registered and `/oauth2/*` is already proxied (`worker/app.ts:361-363`); refresh rotation is built in. The plan is verify + advertise in discovery metadata + document + regression-test, plus a deliberate check of refresh-reuse detection.
- **023 (attack protection):** no rate limiting is configured today and there is no account lockout; the plan adds KV-backed `rateLimit`, identity-keyed lockout layered into the existing `accountSecurityEmailPlugin` after-middleware (`src/lib/auth-server/hooks.ts:167`), and optional risk-based step-up reusing the `twoFactor` plugin + plan-019 `acr`/`amr`. **HIBP / breached-password detection is excluded** by operator decision (paid/external).

Plans 017-020 came from an improve `next` (direction) pass on 2026-06-17 and were **implemented directly** (2026-06-17, v0.0.44–0.0.47) rather than stopping at design docs. What shipped, and where the recon changed the plan:

- **019 (step-up):** recon showed `@better-auth/oauth-provider` 1.6.18 already enforces `prompt=login`/`max_age` and mints `auth_time`/`sid`, and hardcodes a static `acr`. Shipped: truthful tiered `acr` + `amr` via `customIdTokenClaims` (`src/lib/oauth-scope-claims.ts`, overriding the static `acr`), `amr` added to `claims_supported`. Deferred: per-client "require MFA" enforcement (the plugin does not semantically gate on `acr_values`).
- **020 (activity log):** shipped `account_activity_event` table (migration `0007`), recording from the existing auth after-hook independent of email prefs (`src/auth.ts`), a user-scoped `/api/account/activity` service/route, and a feed on the Security page. Taxonomy in `src/lib/account-activity.ts` is the single source of truth for activity + security-alert email wording.
- **017 (webhooks):** shipped `webhook_endpoint` + `webhook_delivery` tables (migration `0008`), HMAC-SHA256 signing + SSRF guard (`src/lib/webhooks.ts`), durable delivery via `WebhookDeliveryWorkflow` (`worker/webhooks.ts`, new wrangler binding), emission from auth hooks + admin user mutations, admin CRUD API, and a new `/admin/webhooks` page. Events: `user.created/deleted/banned/unbanned/role_changed`, `account.linked`.
- **018 (back-channel logout):** recon confirmed RP-initiated logout (`/oauth2/end-session`) already works natively via the `enableEndSession` client flag, and `sid` is emitted. Shipped the missing back-channel push: a `backchannel_logout_uri` client column (migration `0009`, configurable in the Applications UI), spec-correct `logout_token` minting via `auth.api.signJWT` (`src/lib/backchannel-logout.ts`), and best-effort fan-out on **admin ban** (`worker/index.ts`). Deferred triggers: sign-out and account-deletion propagation (reuse the same helper).

## Dependency notes

- 002 should follow 001 because both deal with OAuth client/application concepts. 001 establishes the user-facing distinction between "registered client" and "authorized grant"; 002 then adds operator-owned client management without confusing it with user revocation.
- 003 is independent. It can run before or after the OAuth application work.
- 004 is independent. It is lower priority because current static branding works for a single deployment.
- 005 is independent and should land before future organization-owned OAuth clients, tenant policy, or SCIM/SAML work.
- 006 is independent and should land before admin-only support, audit, or impersonation workflows.
- 007 is independent. If agent controls become admin-owned instead of user-owned, revisit it after 006; the first pass should stay user-owned.
- 008 and 009 are independent small fixes.
- 010 should follow 008 because both touch the Applications/OAuth worker surfaces; this avoids unnecessary merge conflicts. There is no behavioral dependency between pagination and post-logout URI validation.
- 011 is behaviorally independent, but if 010 is still TODO it should land after 010 to reduce conflicts in `worker/app.ts` and `src/pages/Applications.tsx`.
- 012 follows 011 because consent should reuse the custom scope registry and current OAuth client management surfaces.
- 013 follows 006 because admin user governance creates the first operator mutations that need audit history.
- 014 follows 005 and 011 because organization/team lifecycle must exist before team claims can be operationally useful.
- 015 follows 011 and 014 because the `permissions` scope already exists and policy should build on real organization/team membership behavior.
- 016 follows 012-015 because organization-owned OAuth clients need consent metadata, audit events, team membership, and tenant-scoped policy decisions before schema and route work begins.
- 017-020 are mutually independent design plans and may be done in any order. Two pairings matter for the eventual implementations (not the design plans): 018 (back-channel logout) and 017 (webhooks) may share a delivery transport but must keep distinct payloads — OIDC `logout_token` vs custom events; and 020 (activity log) and 017 should keep identical event `type` strings so the same identity event is named consistently across the user feed and outbound webhooks. Priority order if picking one: 017, then 018, then 019, then 020.
- 021 and 022 pair: 022 (introspection/revocation) is how a resource server validates the M2M tokens 021 issues, so build 022 first or alongside 021. Both are largely "turn on + surface + test" because the engine already exists at the installed plugin version; neither should reimplement protocol the plugin provides. 021's M2M doc should link 022's token-validation doc for the resource-server story.
- 023 is independent of 021/022. Its Phase 3 (risk-based step-up) builds on plan 019's `acr`/`amr` and the existing `twoFactor` plugin; if step-up requires forking the sign-in flow, defer it as a separate plan rather than expanding 023. 023 must keep the lockout activity `type` string consistent with the plan-017/020 cross-naming rule.
- Priority order if picking one of 021-023: 022 (highest leverage, lowest build — makes existing capabilities legible), then 021 (the platform-enabling feature), then 023 (security hardening, independent and resumable).

## Findings considered and rejected

- OIDC integration diagnostics page: explicitly skipped by the operator for this planning pass.
- Billing persistence: not worth planning now. The current Account page has non-persistent billing fields, but the product goal and README define Passport as an identity provider, not a billing product.
- Shared UI package for the example client: not worth planning now. The example client is small and can intentionally differ visually while it demonstrates OAuth integration.
- Large dashboard page extraction: valid tech debt, but it should wait until characterization tests cover the high-risk auth flows.
- Runtime config consolidation: useful, but lower leverage than the selected correctness/security/performance fixes.
- Relationships OAuth scope: explicitly deferred. The repo has no relationship data model yet, so exposing a `relationships` scope now would create a misleading provider contract.
- Promote Agent Auth to real account capabilities (DIR-01, 2026-06-17 next pass): grounded — the agent/host/grant/approval infrastructure is fully built but exposes only the read-only `get_service_metadata` capability (`src/auth.ts:226-250`). Held by the operator for now; revisit after webhooks/back-channel logout land.
- SCIM 2.0 provisioning for enterprise tenants (DIR-04, 2026-06-17 next pass): grounded in the org/member/team/role model but demand-gated; held by the operator until there is a concrete enterprise pull. Same status as the per-org SSO connections idea (DIR-07).
- Per-organization SSO connections / tenant IdP federation (DIR-07, 2026-06-17 next pass): large, strategic, demand-gated; not selected this pass.
- Token-verification SDK / npm helper (2026-06-17 next pass): grounded (the example client is the only consumer) but lower leverage than the selected work and adjacent to the already-rejected shared-UI-package idea; a docs page likely suffices.
